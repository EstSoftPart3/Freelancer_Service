B1

재발급 요청에 refresh 토큰 대신 만료된 access 토큰이 실린다

치명초급
위치
frontend/vue_js/src/axios.js:16-27 (요청 인터셉터), :88-94 (재발급 호출)
증상
로그인하고 30분(access 수명)이 지나면 다음 API 호출이나 새로고침 때 무조건 로그아웃됩니다. 14일짜리 refresh 토큰이 있는데도 한 번도 재발급에 성공하지 못합니다.
원인
재발급을 apiInstance.post('/refresh-token', {}, { headers: { Authorization: 'Bearer ' + refreshToken } })로 보내는데, 같은 인스턴스의 요청 인터셉터가 나중에 실행되며 localStorage.accessToken(이미 만료된 토큰)으로 Authorization을 덮어씁니다. 서버는 만료 토큰을 받아 validateToken 실패 → 400 → 프론트 catch에서 clearLoginState().
개선
  • 재발급은 인터셉터가 없는 별도 axios 인스턴스(또는 순수 axios.post)로 보낸다 — BO의 api.ts:89가 이 방식.
  • 또는 요청 인터셉터에서 이미 Authorization이 있으면 건드리지 않는다.
  • 근본적으로는 refresh 토큰을 HttpOnly 쿠키로 옮기면 헤더 조립 자체가 사라진다(V3 참고).

교육생 힌트 · access 만료 시간을 1분(access-token-expiration: 60000)으로 줄이고, 개발자도구 Network 탭에서 /refresh-token 요청의 Authorization 헤더 값을 로그인 응답과 비교해 보세요.

B2

재발급 응답을 response.data.data로 읽는다

치명초급
위치
frontend/vue_js/src/axios.js:97-98 · backend/.../common/ApiResponse.java:13
증상
B1을 고쳐도 재발급 직후 원래 요청이 다시 401이 나고, 그다음 재발급부터는 영원히 실패합니다.
원인
서버 공통 응답은 { status, message, output }인데 인터셉터는 response.data.data.accessToken을 읽어 undefined가 됩니다. localStorage.setItem은 이를 문자열 "undefined"로 저장합니다. 더 나쁜 점은 서버가 이미 refresh 토큰을 회전해 DB의 옛 토큰을 지웠다는 것 — 새 refresh 토큰을 잃어버렸으니 다시는 재발급할 수 없습니다. 로그인 화면(LoginPage.vue:202)은 response.output을 올바르게 읽고 있어 두 코드의 불일치를 대조하기 좋습니다.
개선
  • response.data.output으로 읽고, 값이 없으면 저장하지 말고 즉시 실패 처리.
  • 응답 타입을 한 곳(예: types/api.ts 또는 JSDoc)에 정의해 필드명을 추측하지 않게 한다. BO의 api.ts:103에 있는 data.token ? … : … 식의 "혹시 몰라서" 분기도 같은 병의 증상.

교육생 힌트 · 로그인 성공 코드와 재발급 성공 코드가 응답에서 토큰을 꺼내는 방식을 나란히 놓고 보세요. 재발급 후 localStorage에 무엇이 저장되는지도 확인하세요.

B3

공개 경로에서 토큰이 만료되면 401이 아니라 500이 난다

높음중급
위치
JwtAuthenticationFilter.java:73-89 · ProjectController.java:90-101 · ResumeController.java:43-47
증상
토큰이 만료된 상태로 공고 삭제(DELETE /api/projects/{id})나 이력서 등록(POST /api/mypage/resume)을 하면 500 "알 수 없는 오류"가 뜹니다. 프론트 인터셉터는 401만 재발급 신호로 보므로 재발급이 시도조차 되지 않고, 화면은 로그인 상태 그대로 남습니다.
원인
제외 경로에 해당하면 필터는 토큰이 있지만 무효인 경우에도 조용히 익명으로 통과시킵니다(주석: "토큰 오류 무시하고 통과"). 컨트롤러는 로그인을 전제로 (JwtAuthenticationToken) authentication이나 @AuthenticationPrincipal Long userSq를 쓰다가 null을 만나 NPE → GlobalExceptionHandler가 500으로 변환합니다.
개선
  • "토큰이 없음"과 "토큰이 있는데 무효"를 구분한다. 없으면 익명 통과, 있는데 무효면 공개 경로여도 401.
  • 로그인이 필요한 핸들러는 V2처럼 Security 설정에서 막아 컨트롤러가 null을 받을 일이 없게 한다.

교육생 힌트 · 같은 만료 토큰으로 /api/me와 /api/projects/1(DELETE)을 호출해 응답 코드를 비교하세요. 왜 한쪽은 401이고 한쪽은 500일까요?

실제 운영에서 2026-09-16에 발생해 핫픽스한 버그입니다. "교재용 가상 버그가 아니다"라는 점이 동기 부여에 좋습니다.

B4

인증 실패 응답의 코드와 형식이 경로마다 다르다

중간중급
위치
LoginService.java:73-81 · GlobalExceptionHandler.java:11-15 · AdminAuthController.java:48-55 · JwtAuthenticationFilter.java:93,105 · JwtProvider.java:74-81
증상
같은 "토큰이 틀렸다"는 상황인데 응답이 제각각입니다.
  • FO /refresh-token 실패 → IllegalArgumentException → 400
  • BO /admin/refresh-token → 모든 예외를 401로 (DB 장애도 "다시 로그인하세요")
  • 필터 → response.sendError(401) → 공통 ApiResponse가 아닌 Spring 기본 에러 JSON
원인
인증 전용 예외가 없고, validateToken이 boolean만 돌려줘 "만료"와 "위조"를 구분할 수 없습니다. 프론트는 만료면 재발급, 위조면 즉시 로그아웃을 해야 하는데 판단 근거가 없습니다.
개선
  • ExpiredJwtException과 그 밖의 JwtException을 구분해 에러 코드(TOKEN_EXPIRED / TOKEN_INVALID)를 내려준다.
  • 인증 실패는 항상 401 + 공통 응답 형식. 필터에서는 AuthenticationEntryPoint로 위임해 형식을 한 곳에서 만든다.
  • BO 재발급은 "토큰 문제"만 401, 그 외는 500으로 남겨 장애를 가리지 않는다.

교육생 힌트 · 위조 토큰, 만료 토큰, 빈 토큰으로 /api/refresh-token과 /api/admin/refresh-token을 각각 호출해 상태코드·본문을 표로 만들어 보세요.

B5

prod 보안 설정이 context-path와 어긋나 로그인까지 막힌다

높음중급
위치
SecurityConfigProd.java:36-37 · application.yml server.servlet.context-path: /api
증상
dev 프로필에서는 잘 되다가 prod 프로필로 띄우면 로그인·재발급·게시판 목록 같은 공개 API까지 전부 401이 됩니다.
원인
  • Spring Security의 requestMatchers("/api/login")는 context-path를 뺀 경로(/login)와 비교하므로 절대 매치되지 않습니다. 반대로 커스텀 필터는 getRequestURI()(context-path 포함)로 비교해 /api/login이 맞습니다 — 한 프로젝트에 두 기준이 섞여 있습니다.
  • permitAll이 로그인·재발급 두 개뿐이고 나머지는 anyRequest().authenticated()라, 필터의 공개 목록과 Security 설정이 서로 다른 말을 합니다.
  • dev는 반대로 anyRequest().permitAll()이라 인가 판단이 전부 필터 목록에 떠넘겨져 있습니다(V2의 배경).
개선
공개/인증/관리자 경로를 한 곳(SecurityConfig)에 context-path 없는 경로 + HTTP 메서드로 선언하고, dev/prod가 같은 규칙을 공유하게 한다. 필터는 목록을 갖지 않는다.

교육생 힌트 · --spring.profiles.active=prod로 기동해 로그인해 보세요. 필터의 EXCLUDE_URLS와 requestMatchers가 비교하는 "경로"가 같은 문자열인지 확인하세요.

B6

다른 기기나 다른 탭에서 로그인·재발급하면 기존 세션이 튕긴다

중간중급
위치
UserMapper.xml:66-67 (user_refresh_token 단일 컬럼) · LoginService.java:59, 88
증상
PC에서 로그인한 상태로 휴대폰에서 로그인하면, 30분 뒤 PC가 로그아웃됩니다. 탭 두 개를 열어 둔 채 access가 만료되면 한쪽 탭이 로그아웃되기도 합니다.
원인
사용자당 refresh 토큰을 하나만 저장합니다. 새 로그인이나 재발급이 컬럼을 덮어쓰면 다른 기기가 가진 토큰은 findByRefreshToken에서 조회되지 않습니다. failedQueue는 한 탭 안에서만 재발급을 합쳐 주므로, 두 탭이 거의 동시에 재발급하면 늦은 쪽이 방금 회전된 옛 토큰을 보내 실패합니다.
개선
  • refresh 토큰을 별도 테이블로 분리: (token_id, user_sq, token_hash, device_info, expires_at, revoked_at). 기기마다 한 행.
  • 회전 직후 몇 초간 옛 토큰을 허용하는 유예 시간, 또는 탭 간 동기화(BroadcastChannel / storage 이벤트).
  • "한 기기만 허용"이 정책이라면 그것도 답이 될 수 있음 — 다만 의도로 문서화하고 사용자에게 알린다.

교육생 힌트 · 크롬 일반 창과 시크릿 창에서 같은 계정으로 로그인한 뒤, DB의 user_refresh_token 값이 어떻게 바뀌는지 보세요.

보안 취약점 (V)

V1

refresh 토큰을 access 토큰처럼 써도 통과한다

치명중급
위치
JwtProvider.java:34-59 · JwtAuthenticationFilter.java:92-103
증상
로그인 응답의 refreshToken을 Authorization: Bearer에 넣어 /api/me를 호출하면 200이 납니다. 즉 access 토큰 수명이 사실상 30분이 아니라 14일이고, 로그아웃해도(DB에서 refresh를 지워도) 서명은 여전히 유효하므로 로그아웃 후에도 14일간 API 호출이 가능합니다.
원인
access와 refresh가 같은 키, 같은 클레임(sub, userTypeCd)으로 만들어지고 만료 시간만 다릅니다. 필터는 "서명이 맞고 안 만료됐나"만 보고 토큰의 종류를 검사하지 않습니다. 비밀번호 재설정 토큰도 같은 키로 서명되어 있어(목적은 purpose 클레임으로만 구분) 같은 계열의 혼동이 생길 수 있습니다.
개선
  • 토큰마다 종류 클레임(typ: access|refresh|reset)을 넣고, 필터는 access만, 재발급 API는 refresh만 받는다.
  • 가능하면 용도별로 서명 키를 분리한다(한 키가 새도 다른 용도는 안전).
  • refresh 토큰은 애초에 API 경로로 보내지 않는다(HttpOnly 쿠키 + Path=/api/refresh-token).
# 재현: 로그인 응답의 refreshToken 으로 보호 API 호출
curl -X POST http://localhost:8080/api/me \
  -H "Authorization: Bearer <로그인 응답의 refreshToken>"
# → 200 "내 정보 조회 성공"  (401이어야 정상)
