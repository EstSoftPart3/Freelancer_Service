#### P1 상세 — 왜 그랬는가

이미지는 전부 `/api/files/{uuid}` 로 서빙되는데
`SecurityConfigProd.java` 의 permitAll 목록에 `/uploads/**` 만 있고 `/files/**` 가 없었다.
`<img>` 요청에는 axios 인터셉터가 붙이는 Authorization 헤더가 없어 **401**.
dev 프로파일은 `anyRequest().permitAll()` 이라 로컬에서는 재현조차 안 된다.

`JwtAuthenticationFilter.EXCLUDE_URLS` 에는 `/api/files` 가 이미 있었다.
그 파일 주석이 경고하던 "한쪽만 넣으면 설정상 공개인데 실제로는 401" 이 그대로 일어난 것.

함께 고친 것
- `FileController` : `Files.probeContentType` 이 리눅스 컨테이너에서 null → 확장자 기반 판정으로
- `FileStorageService` : 변환 전 확장자로 파일명을 만들어 `.gif` 이름의 JPEG 가 생기던 문제

## 🔴 아직 안 끝난 것 — P1 최종 검증

P1(프로필 이미지 401)은 **dev 프로파일이 `anyRequest().permitAll()` 이라 로컬에서 재현조차 안 된다.**
실서버에서 확인하는 게 유일한 수단인데, **지금은 시험할 uuid 가 없다** —
P6-1 초기화로 `TBL_COMMON_FILE_S` 가 0행이고 P6-5 로 업로드 디렉터리도 비웠다.

**그래서 순서가 이렇다 : 파일을 하나 올린다 → 그 uuid 로 확인한다.**
공고 이미지든 프로필 사진이든 상관없다. 로그인이 필요해 사람이 해야 한다.

```bash
curl -i https://job.estsw.co.kr/api/files/<uuid>
```
| 결과 | 뜻 |
|---|---|
| **200 + `Content-Type: image/*`** | 성공 |
| 401 | `SecurityConfigProd` 미반영 — 백엔드 재빌드/재기동 확인 |
| 500 | 원인이 다름 — `FILE_ENCRYPT_KEY` 불일치 |
| `application/octet-stream` | MIME 판정이 덜 됨 — `FileController` 반영 확인 |

브라우저(시크릿 창) 육안 확인 — 자산 200 은 curl 로 이미 확인했고, 배치는 눈으로 봐야 한다:
- [ ] 헤더·푸터에 **로고 이미지**가 뜨는가 (텍스트 "Ctrl + F" 가 아니라)
- [ ] 브라우저 탭에 **파비콘**이 뜨는가
- [ ] 메인 캐러셀에 **광고 배너 3장**이 뜨는가

### 🔴 이때 겪은 함정

**"회원 유형이 일치하지 않습니다" 로 로그인이 안 된다** → 십중팔구 **변환이 아직 반영 안 된 것**이다.
이 스크립트의 **드라이런은 실제로 DELETE/INSERT 를 실행한 뒤 ROLLBACK 한다**(제약 위반을 미리
잡으려는 설계). 그래서 드라이런 출력에도 `user_sq=…` `company_sq=…` 가 멀쩡히 찍힌다 —
**출력만 보고 반영됐다고 착각하기 쉽다.** 마지막 줄이 `✅ 커밋했다.` 인지 확인할 것.

메커니즘 : `LoginService.java:47` 이 계정의 `user_type_cd` 와 **로그인 화면에서 고른 탭**을 비교한다.
`LoginForm.tsx:58` 은 개인 탭 → 301, 기업 탭 → 302 만 보낸다.
관리자(303) 계정은 FO 에 해당 탭이 없어 **어느 탭을 눌러도 이 에러가 난다.**

### 🔴 실제 사업자번호로 인증하려면 — FO 가 아니라 **BO** 에서

`AffiliationEditClient.tsx:208` 의 "지금 바로 기업 인증하기" 버튼은 `{!isAuthorized && (...)}` 안에 있고
`isAuthorized = companyAuthStatusCd !== '2501'` 이다. → **2502 면 버튼이 아예 렌더되지 않는다.**
대표자명·기업명·개업일자도 그 화면에서는 읽기 전용이라 **FO 만으로는 고칠 방법이 없다.**

**BO → 매니지먼트 → 유저 관리 → 소속 관리(`/management/company`)** → 기업 상세 다이얼로그를 쓴다
(`features/users/components/company-details-dialog.tsx`). 여기는 인증 상태와 무관하게 항상 열려 있다.

1. 인증 필드 4개(기업명·대표자명·사업자번호·개업일자)에 실제 값 입력
2. **인증하기** → `/mypage/edit/verify-enterprise` (FO 와 같은 국세청 진위확인 API)
3. 성공해야 저장이 열린다 (`canSave = hasAllAuthFields && isVerified`)
4. **저장** → `updateCompany` 가 인증 4필드 + `company_auth_status_cd=2502` 를 한꺼번에 덮어쓴다

- 🔴 **인증하면 `company_nm` 도 국세청 상호로 덮어쓴다 — "Ctrl + F" 가 사라진다.**
  브랜드명을 유지하려면 인증 후 같은 다이얼로그에서 기업명만 다시 고칠 것
  (인증 필드를 안 건드리면 `companyAuthStatusCd` 를 안 보내서 2502 는 유지된다)
- 🔴 **`000-00-00000` 은 오픈 전 반드시 교체할 것.** `findUserRole` 이 bizNum 동일성으로
  `COMPANY_AUTHOR`/`COMPANY_MEMBER` 를 가른다 — 다른 기업 계정에 같은 자리표시자가 들어가면
  **서로 같은 소속으로 잘못 판정된다.** 지금은 기업이 하나뿐이라 문제없다
- 같은 다이얼로그에서 주소도 고칠 수 있는데, `updateCompany` 가 `TBL_ADDRESS_S` 를
  `c.address_sq` **조인**으로 갱신하는 구조라 위 ① 보완이 전제조건이었다.
  그 전이었다면 BO 에서 주소를 고쳐도 **조용히 아무것도 안 바뀌었을 것**이다
- (미해결) FO 는 이미 인증된 기업이 정보를 못 고친다. 오타를 내면 BO 를 거쳐야만 고쳐진다.
  고치려면 `AffiliationEditClient` 에 재인증 진입점 추가 + FO 재빌드·배포가 필요하다

## 서버 기동 방법 (메모리에 있는 규칙)

```bash
# 백엔드 — cmd.exe 래핑 금지, run_in_background 로
cd backend && ./gradlew bootRun

# FO — 언제나 dev:clean (그냥 dev 금지)
cd frontend/nextjs && npm run dev:clean

# BO — 5173 고정 (CORS)
cd frontend/react_js && npm run dev
```
BO 로그인 : `admin` / `{{ADMIN_PW}}`

🔴 **띄우기 전에 포트 점유부터 확인할 것.** 백그라운드 태스크를 종료해도
**래퍼 셸만 죽고 node/java 프로세스는 살아남는다.** 그러면 FO 가 3000 이 아닌 **3001** 로 밀리고,
두 dev 서버가 같은 `.next` 를 공유해 상세 페이지가 `Jest worker ...` 500 을 뱉는다.
`dev:clean` 을 다시 돌려도 낫지 않는다 — 남은 프로세스를 죽여야 한다. (2026-08-26 에 겪음)

```powershell
Get-NetTCPConnection -LocalPort 3000,3001,8080,5173 -State Listen |
  ForEach-Object { "{0}  PID={1}" -f $_.LocalPort, $_.OwningProcess }
Stop-Process -Id <pid> -Force
```
→ 기동 로그에 **3001** 이 찍히면 이미 이 상태다.
