# 원격 관리 수단 구축 (요구사항)

> 작성 2026-08-03 · 계기: 사무실 밖에서 Cloudflare Tunnel 이 끊겨 **복구할 방법이 없었다**

---

## 1. 무엇이 문제인가

2026-08-03 조사 중 `job`·`admin-job`·`www` 등 estsw.co.kr 전 도메인이 동시에
**530 (`error code: 1033`)** 이 됐다. Cloudflare Tunnel 이 끊긴 것이다.

그때 할 수 있는 게 아무것도 없었다:

| 경로 | 가능? | 이유 |
|---|---|---|
| SSH (`192.168.2.104`) | ❌ | 내부망 전용. 외부에서 도달 불가 |
| SSH (공인 도메인) | ❌ | 22번 포트 미노출. Cloudflare 프록시는 HTTP/HTTPS 만 통과 |
| CasaOS UI (`casa.estsw.co.kr`) | ❌ | **같은 터널에 물려 있어 함께 죽는다** |
| 도커 재시작 | ❌ | 위 셋 중 하나가 있어야 가능 |

**핵심 결함은 관리 경로가 장애 대상과 같은 터널을 공유한다는 것이다.**
터널이 살아 있을 때만 쓸 수 있는 관리 수단은 정작 필요한 순간에 없다.

---

## 2. 권장안 — Tailscale (터널과 독립된 경로)

Cloudflare Tunnel 과 **완전히 별개**인 오버레이 네트워크를 하나 더 둔다.
터널이 죽어도 서버 인터넷 연결만 살아 있으면 들어갈 수 있다.

### 왜 이걸 권하는가

- 터널·NPM·포트포워딩 어디에도 의존하지 않는다 → **단일 장애점이 사라진다**
- 공유기 포트를 열지 않는다 → 공격면이 늘지 않는다
- 무료 요금제로 충분하다(개인 20대까지)
- 설치 5분, 모바일 앱으로도 접속된다

### 설치 (서버, 1회)

```bash
curl -fsSL https://tailscale.com/install.sh | sh
sudo tailscale up
# 출력되는 URL 을 브라우저에서 열어 계정으로 로그인 → 승인
tailscale ip -4        # 100.x.x.x 형태의 주소가 나온다. 이게 어디서든 닿는 주소다
```

**Tailscale SSH 를 켜면** 키 관리 없이 접속된다(권한은 Tailscale 정책이 판단):

```bash
sudo tailscale up --ssh
```

### 클라이언트 (노트북·휴대폰)

1. https://tailscale.com/download 에서 설치 후 **같은 계정**으로 로그인
2. 접속:

```bash
ssh estsoft@100.x.x.x          # tailscale ip -4 로 확인한 주소
# 또는 머신 이름으로
ssh estsoft@estsoft
```

이러면 카페든 집이든 **터널 상태와 무관하게** 서버에 들어가 `docker restart cloudflared-tunnel` 을 할 수 있다.

### 검증

설치 후 반드시 **다른 네트워크에서** 한 번 접속해볼 것(휴대폰 테더링 등).
사무실 안에서만 확인하면 내부망으로 붙은 건지 Tailscale 로 붙은 건지 구분되지 않는다.

## 3. 대안 — Cloudflare Tunnel 로 SSH 노출

이미 `cloudflared` 를 쓰고 있으니 추가 설치 없이 된다. **다만 터널이 죽으면 이것도 죽는다** —
일상적인 원격 작업에는 편하지만 이번 같은 장애의 해결책은 아니다.

### 설정 (Cloudflare Zero Trust 대시보드)

1. Networks → Tunnels → 기존 터널 선택 → **Public Hostname** 추가
   - Subdomain `ssh`, Domain `estsw.co.kr`
   - Service: **`SSH`**, URL `localhost:22`
2. Access → Applications → **Self-hosted** 앱 생성
   - Domain `ssh.estsw.co.kr`
   - Policy: 허용할 이메일(구성원)만 — **이걸 빼면 인터넷 전체에 SSH 가 열린다**

### 클라이언트

```bash
# cloudflared 설치 후 ~/.ssh/config 에 추가
Host ssh.estsw.co.kr
  ProxyCommand cloudflared access ssh --hostname %h
  User estsoft
```

```bash
ssh ssh.estsw.co.kr
```

> **공유기 포트포워딩(22번 개방)은 권장하지 않는다.** 공인 IP 에 SSH 를 직접 노출하면
> 자동화된 무차별 대입 시도가 곧바로 들어온다. 굳이 한다면 비밀번호 인증을 끄고
> 키 인증만 허용하며 포트를 바꾸고 fail2ban 을 걸어야 하는데, Tailscale 이 훨씬 싸게 먹힌다.

## 4. 터널이 스스로 복구되게 하기

사람이 개입하기 전에 자동으로 살아나는 게 최선이다.

### 4-1. 재시작 정책 확인

```bash
docker inspect cloudflared-tunnel --format '{{.HostConfig.RestartPolicy.Name}}'
```

`no` 나 빈 값이면 컨테이너가 죽었을 때 다시 뜨지 않는다. 바꾼다:

```bash
docker update --restart unless-stopped cloudflared-tunnel
```

> 단 이건 **프로세스가 죽었을 때**만 듣는다. 컨테이너는 살아 있는데 터널 연결만 끊긴
> 경우(이번 사례로 의심되는 상황)에는 동작하지 않는다 → 4-2 가 필요하다.

### 4-2. 외형 감시 + 자동 재시작

실제 응답을 확인하고, 연속 실패하면 재시작한다.

```bash
sudo tee /usr/local/bin/tunnel-watchdog.sh > /dev/null <<'EOF'
#!/bin/bash
# Cloudflare Tunnel 감시 — 외부에서 본 응답이 연속 실패하면 컨테이너를 재시작한다.
URL="https://job.estsw.co.kr/"
STATE="/tmp/tunnel-fail-count"
LOG="/var/log/tunnel-watchdog.log"

code=$(curl -s -o /dev/null -w '%{http_code}' -m 15 "$URL")
# 2xx·3xx 는 정상. 530/1033 은 터널 장애, 000 은 네트워크 자체 실패.
if [[ "$code" =~ ^[23] ]]; then
  echo 0 > "$STATE"
  exit 0
fi

fails=$(( $(cat "$STATE" 2>/dev/null || echo 0) + 1 ))
echo "$fails" > "$STATE"
echo "$(date '+%F %T') code=$code fails=$fails" >> "$LOG"

# 2회 연속(=약 4분) 실패해야 재시작한다. 순간적인 실패로 재시작을 반복하지 않기 위함이다.
if [ "$fails" -ge 2 ]; then
  echo "$(date '+%F %T') restarting cloudflared-tunnel" >> "$LOG"
  docker restart cloudflared-tunnel >> "$LOG" 2>&1
  echo 0 > "$STATE"
fi
EOF

sudo chmod +x /usr/local/bin/tunnel-watchdog.sh

# 2분마다 실행
( crontab -l 2>/dev/null; echo "*/2 * * * * /usr/local/bin/tunnel-watchdog.sh" ) | crontab -
crontab -l
```

⚠️ **주의** — 이 스크립트는 서버가 자기 자신을 외부 도메인으로 확인한다. 사내망에서
`job.estsw.co.kr` 이 내부 IP 로 해석되면 터널을 우회해 항상 성공할 수 있다.
그럴 땐 `curl --resolve` 로 Cloudflare IP 를 강제하거나, 외부 감시(4-3)를 함께 쓴다.

### 4-3. 외부에서 감시 + 알림 (이미 있는 도구 활용)

서버에 **Uptime Kuma 가 이미 돌고 있다**(`status.estsw.co.kr`, 포트 3001).
다만 서버 안에 있으므로 서버가 통째로 죽으면 알림도 못 준다 → **외부 감시를 하나 더** 두는 게 좋다.

- Uptime Kuma 에 `https://job.estsw.co.kr` 모니터 추가 → 알림을 **카카오톡·이메일·Slack** 으로
- 외부 무료 서비스(UptimeRobot 등)에도 같은 URL 을 하나 걸어두면 서버 전체 장애도 잡힌다

감지가 되면 Tailscale 로 들어가 조치하면 된다.

## 5. 권장 조합

| 층 | 수단 | 효과 |
|---|---|---|
| **예방** | `restart: unless-stopped` (4-1) | 프로세스 죽음 자동 복구 |
| **자동 복구** | watchdog cron (4-2) | 연결만 끊긴 경우 자동 복구 |
| **감지** | Uptime Kuma + 외부 감시 (4-3) | 장애를 사람이 곧바로 안다 |
| **최후 수단** | **Tailscale (2)** | 어떤 상황에서도 서버에 들어갈 수 있다 |

**우선순위** — Tailscale(2) 과 재시작 정책(4-1) 을 먼저 하면 이번 같은 상황이 재발해도
5분 안에 복구할 수 있다. watchdog 과 알림은 그다음이다.
