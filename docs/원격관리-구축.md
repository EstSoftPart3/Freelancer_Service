## 3. 고친 것 — watchdog 이 회선 장애를 터널 장애로 오판했다

### 문제

`watchdog.sh` 의 판정 로직이 이랬다.

```
외부 전부 실패 + 내부 전부 정상  →  NPM 이 정상이면 "터널 문제"  →  터널 재시작
```

**랜선이 빠져도 증상이 정확히 이것이다.** 그래서 `"NPM 은 정상이나 외부 전체 불가 -> 터널 문제"`
로 판정하고 **22시간 동안 85회 재시작**했다. 회선이 없으면 터널은 뜰 수 없으므로 전부 무의미했고,
인시던트 기록에도 잘못된 원인이 남았다.

### 조치 (2026-08-04 적용 완료)

`lib.sh` 에 `uplink_ok()` 를 추가하고, `watchdog.sh` 가 **터널/NPM 을 정하기 전에** 호출하게 했다.
업링크가 죽었으면 재시작하지 않고 정확한 사유로 알림만 남긴다(회선 복구 시 발송된다).

확인 순서 — 좁은 것부터:

1. **기본 경로·게이트웨이 ping** → 랜선 분리·공유기 다운
2. **공인망 도달(`https://1.1.1.1/`, DNS 안 탐)** → 공유기는 살아있고 ISP 회선만 죽은 경우
3. **DNS 조회(`cloudflare.com`)** → 회선은 살아도 리졸버가 죽은 경우
   (cloudflared 는 SRV 조회에 실패하면 스스로 종료하므로 이게 곧 터널 다운이다)

검증 결과 — 문법검사 통과 / 정상 상태 `반환=0` / 게이트웨이 무응답 시뮬 `반환=1, 사유="게이트웨이
무응답 - 랜선 분리 또는 공유기 다운"` / 수동 실행 종료코드 0 / cron 오류 없음.

수정 전 원본은 `~/monitoring/backup-20260804-0915/` 에 있다.

## 4. 남은 약점과 보완안

### 4-1. DNS 단일 장애점 — 효과가 제한적이라 보류 (2026-08-04 재검토)

```
Current DNS Server: 192.168.2.1      ← 공유기 하나뿐
```

**초판에 적었던 `FallbackDNS=` 방법은 동작하지 않는다.** `man resolved.conf` 확인 결과:

> FallbackDNS= ... **This setting is hence only used if no other DNS server information is known.**

DHCP 로 `192.168.2.1` 이 이미 잡혀 있으므로, 그것이 응답하지 않아도 `FallbackDNS` 는
**절대 사용되지 않는다.** 초판의 설정은 아무 효과가 없다.

**그리고 더 중요한 것 — 이번 장애에는 애초에 도움이 되지 않았다.**
랜선이 빠진 상태에서는 공인 리졸버든 공유기든 **아무 DNS 도 닿지 않는다.**
DNS 다중화가 의미 있는 경우는 "회선은 살아 있는데 공유기의 DNS 기능만 죽은" 좁은 시나리오뿐이다.

제대로 하려면 netplan 에서 링크의 nameservers 를 직접 지정해야 한다.

```yaml
# /etc/netplan/*.yaml
    ethernets:
      enp2s0:
        nameservers:
          addresses: [192.168.2.1, 1.1.1.1, 8.8.8.8]
        dhcp4-overrides:
          use-dns: false      # 이게 없으면 DHCP 가 덮어써서 무효가 된다
```

⚠️ 원격에서 netplan 을 잘못 건드리면 네트워크가 끊겨 **내부망에서도 접속이 불가능**해진다
(`netplan try` 로 자동 롤백을 걸고 할 것). 효과 대비 위험이 커서 **보류**한다.
서버 앞에 물리적으로 접근할 수 있을 때 하는 편이 낫다.

이건 고칠 수 있는 버그가 아니라 구조적 한계다.

서버 안쪽 감시는 **이미 완비돼 있다** — Uptime Kuma 가 외부 4개(공개 도메인) + 내부 5개(오리진)를

### 4-3. 원격 접속 수단 (미조치)

장애를 알았어도 **밖에서 서버에 들어갈 방법이 없었다.**

| 경로 | 가능? | 이유 |
|---|---|---|
| SSH `192.168.2.104` | ❌ | 내부망 전용 |
| SSH 공인 도메인 | ❌ | 22번 미노출. Cloudflare 는 HTTP/HTTPS 만 통과 |
| CasaOS UI `casa.estsw.co.kr` | ❌ | **같은 터널에 물려 있어 함께 죽는다** |

단 이번 원인(랜선 분리)은 **어차피 물리적 조치가 필요했으므로** 원격 접속이 있었어도 못 고쳤다.
그래도 공유기 다운·터널 설정 문제 등 원격으로 고칠 수 있는 장애가 더 많으므로 갖춰둘 가치가 있다.

**Tailscale** 을 권한다 — Cloudflare Tunnel 과 독립된 경로라 터널이 죽어도 들어갈 수 있고,
공유기 포트를 열지 않아 공격면이 늘지 않는다.

```bash
curl -fsSL https://tailscale.com/install.sh | sh
sudo tailscale up --ssh
tailscale ip -4        # 100.x.x.x — 어디서든 닿는 주소
```

클라이언트(노트북·휴대폰)에 같은 계정으로 로그인 후 `ssh estsoft@100.x.x.x`.

> **반드시 다른 네트워크에서 접속을 검증할 것.** 사무실 안에서만 확인하면 내부망으로 붙은 건지
> Tailscale 로 붙은 건지 구분되지 않는다.

> 공유기 포트포워딩(22번 개방)은 권하지 않는다. 공인 IP 에 SSH 를 직접 노출하면 자동화된
> 무차별 대입이 곧바로 들어온다.

## 6. 장애 시 확인 순서 (실전)

```bash
# 1) 물리 계층부터 — 이번 원인이 여기였다
ip link show                          # 랜선: state UP 인지
ping -c 2 192.168.2.1                 # 공유기

# 2) 이름 해석
getent hosts cloudflare.com
resolvectl status | head -20

# 3) 터널
docker logs --tail 50 cloudflared-tunnel
docker ps --filter name=cloudflared    # Up 시간이 짧으면 재시작 반복 중

# 4) 감시 시스템이 이미 판단해둔 것
tail -30 ~/monitoring/events.log
tail -40 ~/monitoring/undelivered_alerts.log    # 못 보낸 알림 = 장애 이력
ls -t ~/monitoring/incidents | head -5          # 최근 인시던트 증거
```

텔레그램에서 `/status`·`/incidents` 로도 같은 내용을 볼 수 있다(인터넷이 살아 있을 때).
