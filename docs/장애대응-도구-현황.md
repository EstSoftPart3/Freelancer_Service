# 장애 대응 도구 현황

> 2026-09-23 기준, 운영 서버(`192.168.2.104`)에서 설정값을 직접 확인해 정리.
> 계정·URL·장애 대응 절차의 정본은 [`배포-환경-인계.md`](배포-환경-인계.md).

**한 줄 요약** — Docker·watchdog 이 **고치고**, kuma·UptimeRobot·텔레그램이 **알리고**,
텔레그램 봇으로 **원격 대응**하고, 인시던트 기록·Dozzle 로 **원인을 찾는다.**

## 1층. 자동 복구 — 사람 없이 스스로 고친다

| 도구 | 하는 일 |
|---|---|
| **Docker 재시작 정책** | 컨테이너 13개 전부 `unless-stopped`/`always`. 프로세스가 죽거나 서버가 재부팅되면 Docker 가 다시 띄운다 |
| **watchdog** (`~/monitoring/watchdog.sh`, cron 1분) | 서비스 4개(홈페이지·Nextcloud·프리랜서 Web·Admin)를 **내부·외부 양쪽**에서 확인하고 원인을 갈라 해당 부분만 재시작 |

### watchdog 판정 순서
1. **3회 연속** 실패해야 조치 (1회 실패로는 아무것도 안 함)
2. 내부도 실패 → **앱 문제** → 그 앱 컨테이너 재시작
3. 외부만 실패 → **경로 문제** → 터널(cloudflared) 또는 NPM 재시작
4. 인터넷 회선 자체가 끊김 → 재시작해도 소용없으므로 **알림만** (2026-08-04 추가)
5. 터널 연결이 정상(`cloudflared_tunnel_ha_connections` ≥ 1)이면 **서버→Cloudflare 헤어핀 경로 불안정**으로 보고 재시작 생략.
   단 15분(`TUNNEL_FORCE_AFTER`) 연속 실패면 기존대로 재시작 (2026-09-23 추가)
6. Redis 는 "살아 있는데 응답 없음(행)" 상태까지 PING 으로 잡는다

### 폭주 방지 장치
| 장치 | 값 | 이유 |
|---|---|---|
| 쿨다운 | 터널·NPM 10분 / 앱·Redis 5분 | 같은 대상을 연달아 재시작하지 않음 |
| 서킷 브레이커 | 1시간 4회 초과 시 자동조치 중단 + 사람 호출 | 2026-07-28 재시작 폭주 재발 방지 |
| 일시정지 | 텔레그램 `/pause`, `/resume` | 점검 중 자동조치 끄기 |

## 2층. 감시·알림 — 이상을 알려 준다

| 도구 | 하는 일 |
|---|---|
| **Uptime Kuma** (`status.estsw.co.kr`) | 모니터 9개(외부 4·내부 5) 1분 간격. Down/Up 을 텔레그램으로 알림. **고치지는 않음.** 외부 모니터는 5회 재시도 후 Down (2026-09-23 3→5) |
| **UptimeRobot** (외부 SaaS) | **진짜 서버 바깥**에서 5분 간격 확인. 서버가 통째로 인터넷에서 끊기면 서버 안 도구는 알림조차 못 보내므로, 그때 알려 줄 수 있는 유일한 수단. 감시 주소 4개: `www`·`cloud`·`job`·`admin-job` |
| **텔레그램 알림** | watchdog·kuma 공용. 같은 알림은 30분 안에 억제. 전송 실패분은 `~/monitoring/undelivered_alerts.log` |
| **정기 리포트** | 매일 09:00 텔레그램으로 서버 상태 요약. 중지된 컨테이너가 있으면 경고 |

> kuma 는 서버 **안에서** 외부 주소를 부르므로(헤어핀 경로) 오탐이 생길 수 있다.
> kuma 만 울리고 UptimeRobot 이 조용하면 실사용자 영향은 없었을 가능성이 높다.

## 3층. 원격 조작 — 밖에서 사람이 대응한다

**텔레그램 봇** (`control.sh`). SSH 는 내부망 전용이라 외부에서는 사실상 유일한 조작 수단.

| 명령 | 기능 |
|---|---|
| `/status` | 서비스별 현재 상태. 🟢 = 정상 코드(홈페이지 `200`, 나머지 `200`·`302`) |
| `/incidents`, `/why <ID>` | 최근 인시던트 목록 / 특정 인시던트 원인 상세 |
| `/logs`, `/ps`, `/df` | 컨테이너 로그 / 실행 목록 / 디스크 용량 |
| `/restart` | 컨테이너 수동 재시작 |
| `/pause`, `/resume` | 자동조치 일시정지 / 재개 |

> `302` 는 리다이렉트 응답이다. `cloud.estsw.co.kr` 은 비로그인 접속을 `/login` 으로 302 보내므로 정상이다.

## 4층. 사후 분석 — 왜 죽었는지 파악한다

| 도구 | 하는 일 |
|---|---|
| **인시던트 기록** (`~/monitoring/incidents/`, `incidents.jsonl`) | watchdog 이 조치할 때마다 컨테이너 상태·로그·네트워크를 자동 수집. 요약에 `[장애 HH:MM~HH:MM, N분]` 표기 (2026-09-23 추가) |
| **events.log** | watchdog 의 매분 판정 기록. **다운 감지 자체는 여기에만** 남는다 (`실패 (n/3)`) |
| **장애 대시보드** (`incident-web`, 8090 포트) | 인시던트 이력을 웹으로 표시 (10분마다 갱신) |
| **Dozzle** (`log.estsw.co.kr`) | SSH 없이 브라우저에서 컨테이너 로그 조회 |

### 인시던트 결과값 읽는 법
| 결과 | 의미 |
|---|---|
| ✅ 복구됨 | 재시작 30초 뒤 **1회** 확인 성공. 이후 재발 여부는 `events.log` 로 볼 것 |
| 🚨 복구실패 | 재시작했는데 여전히 실패 |
| ⏸ 조치보류 | 쿨다운·서킷 브레이커로 재시작 안 함 |
| ℹ️ 조치생략 | 터널 정상 → 헤어핀 경로 불안정으로 판단, 재시작 안 함 |
| 업링크장애 | 서버 인터넷 회선 단절 |
