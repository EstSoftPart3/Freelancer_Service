# 이식용 프롬프트 — 기능별 코드리뷰 야간 자동화

> 새 Phase(또는 새 저장소)에서 같은 체계를 세울 때 **아래 코드블록 전체를 그대로 붙여넣는다.**
> 대괄호 부분만 그 프로젝트에 맞게 바꾸면 된다.
> 2026-09-08 Phase1 에서 실제로 돌려보고 다듬은 판이다.

```
기능별로 /code-review 를 반복 실행해서, 새 지적이 안 나올 때까지 검사하고 고치는 체계를 세워줘.
아래 조건을 그대로 지켜줘.

## 1. 범위 나누기
- 리뷰 대상은 `git diff [기준브랜치]...HEAD` 다.
- 이걸 기능 단위 10~15개 그룹으로 쪼개라. 백엔드는 도메인별, 프런트는 화면·기능별로.
- 한 그룹이 너무 크면(50파일 넘으면) 더 쪼개라.

## 2. 🔴 base 함정 — 이걸 놓치면 리뷰가 통째로 헛돈다
`/code-review <경로>` 만 주면 diff base 를 **워킹트리**로 잡는다.
브랜치가 이미 origin 에 push 되어 있으면 origin 기준 diff 가 비어서
"변경 없음" 으로 판정하고 아무것도 안 본다.

→ 리뷰 args 에 반드시 이렇게 명시해라:
  "워킹트리 diff 가 아니라 `git diff [기준브랜치]...HEAD -- <경로>` 를 기준으로 볼 것.
   이 브랜치는 이미 origin 에 push 되어 있어 origin 기준 diff 는 비어 있다.
   미커밋 변경이 있으면 그것도 함께 본다."

## 3. 반복 규칙
- 한 그룹당 **최대 5회차**. 신규 지적이 0건이면 그 전에 끝낸다.
- 회차마다 **「같은 버그가 이웃 메서드·이웃 테이블·이웃 컨트롤러에 남아 있는가」를 최우선으로** 보라고 지시해라.
  실제로 회차마다 나온 것의 대부분이 이 유형이었다(복사-수정으로 만든 코드가 많으면 특히).
- **재지적 금지 목록**을 진행상황 파일에 관리하고, 매 회차 args 에 통째로 넣어라.
  안 넣으면 이미 판단이 끝난 걸 회차마다 다시 올린다.

## 4. 진행상황 파일 (정본)
`[문서경로]/코드리뷰-진행상황.md` 를 만들고 여기에 전부 기록해라.
- 그룹 표(경로 + 상태: 대기/진행중/완료)
- 실행 규칙, base 함정, 재지적 금지 목록
- 「판단 대기」 절 — 야간에 못 고친 정책·설계 판단 건
- 회차 기록(회차·발견·수정·심각도)
이 파일이 정본이다. 사람이 손으로 상태를 바꿔도 다음 실행이 그대로 따른다.
가능하면 gitignore 되는 폴더에 둬서 자동화 산출물이 커밋에 섞이지 않게 해라.

## 5. 야간 무인 자동화
CronCreate 로 `7 18-23,0-4 * * *` (18:07~04:07 매시, 11회) 를 걸어라.

**05시 이후로는 발화하면 안 된다.** 5시간 사용량 블록은 발화 횟수가 아니라
「첫 요청 시각부터 5시간」을 점유한다. 06시에 한 번만 발화해도 11시까지 물려서
근무시간을 잠식한다. 04:07 을 그날의 마지막 발화로 두면
블록이 05:07 에 닫히고 09시에 새 블록이 깨끗하게 열린다.

무인 실행 프롬프트에 반드시 넣을 것:
- **AskUserQuestion 금지.** 밤에는 답할 사람이 없다.
- **명백한 버그만 수정** — null 가드, 권한 누락, NPE, 언박싱 비교, 오타 수준.
- 정책·설계 판단이 걸린 건은 **고치지 말고** 「판단 대기」 에 근거와 재현 시나리오를 적는다.
- 매 회차 끝에 컴파일/빌드로 확인하고, 깨지면 그 수정을 되돌리고 「판단 대기」 에 적는다.
- 429(한도 초과)면 아무것도 하지 말고 조용히 끝낸다. 다음 발화에서 자동 재개된다.
- 보고는 한 줄로. 사람은 자고 있다.

## 6. 커밋 정책
- 그룹이 완료될 때 한 번만 커밋한다. **push 는 하지 않는다.**
- 자동화를 켜기 전에 현재 수정분을 먼저 커밋해서 롤백 지점을 만든다.

## 7. 새 기능이 들어왔을 때
리뷰가 도는 중에 새 기능이 커밋되면 그 코드가 속한 그룹을 **`대기` 로 되돌린다.**
`완료` 로 남기면 새 코드가 한 번도 검사되지 않고 넘어간다.

## 8. 알아둘 것
- cron job 은 **세션 메모리에만** 산다. `/clear` 하면 사라지니, 퇴근 전에 다시 걸어야 한다.
  진행상황 파일에 재생성 방법을 적어둬라.
- 터미널을 켜둔 채 퇴근해야 한다. cron 은 REPL 이 유휴일 때만 발화한다.
- recurring cron 은 7일 후 자동 만료된다.
- 리뷰 1회차는 서브에이전트 기준 **15~19만 토큰**, 8~10분 걸린다. 예산을 이걸로 계산해라.

먼저 그룹을 나눠서 보여주고, 진행상황 파일을 만든 다음, 첫 그룹부터 시작해줘.
```

## 왜 /goal 도 /loop 도 안 쓰는가

**`/loop` 를 쓰지 않는다.** `/loop` 는 단순 인터벌(`*/30 * * * *` 같은)만 만들 수 있어서
**「18시~04시에만」을 표현하지 못한다.** 24시간 내내 돌아 근무시간 블록을 잠식한다.
그래서 프롬프트가 `CronCreate` 로 `7 18-23,0-4 * * *` 를 직접 걸게 했다.
시간대 제어가 이 설계의 핵심이다.

**`/goal` 도 쓰지 않는다.** goal 은 "전부 완료" 될 때까지 매 턴 미충족 알림을 낸다.
야간 cron 에 인계하는 구조에서는 낮 내내 재촉만 하게 되고, 낮에 리뷰를 돌리면
정작 밤에 쓸 예산이 사라진다. 진행 상태는 goal 이 아니라
**진행상황 파일**이 들고 있게 하는 편이 낫다.

→ 위 코드블록을 **그냥 그대로 보내면 된다.** 추가 명령은 필요 없다.
   Claude 가 그룹을 나누고 → 진행상황 파일을 만들고 → cron 을 걸고 → 첫 그룹을 시작한다.

## 오후에 작업할 때 (블록이 밀린다)

5시간 블록은 「첫 요청부터 5시간」을 점유하므로, **오후 작업 시각이 야간 배치를 통째로 밀어낸다.**

| 오후 마지막 요청 | 그 블록 | 18:07 발화 | 결과 |
|---|---|---|---|
| 13시 이전 | 18시 전에 닫힘 | 새 블록 시작 | ✅ 04:07 종료, 09시 클린 |
| 16시 | 16–21시 | 기존 블록에 얹힘 | ❌ 야간이 밀려 04–09시 블록 발생 → 09시 침범 |

**오후 작업은 13시 이전에 마무리하는 것이 원칙이다.**
그날 늦게까지 일했다면 **cron 시작 시각을 그만큼 늦춰라** —
16시까지 일했으면 블록이 21시에 닫히므로 `7 21-23,0-4 * * *` 로 바꾼다.

## 시간대 설계 (5시간 블록)

| 블록 | 시간 | 용도 |
|---|---|---|
| 야간 1 | 18–23 | 자동 리뷰 |
| 야간 2 | 23–04 | 자동 리뷰 |
| 야간 3 | 04–09 | 자동 리뷰 |
| 근무 1 | 09–14 | 다른 작업 |
| 근무 2 | 14–19 | 다른 작업 |

야간 3블록이 09시에 정확히 닫히고 근무시간 블록 2개가 온전히 열린다.
**전제**: 퇴근 전 마지막 요청이 13시 이전이어야 18시에 새 블록이 열린다.
