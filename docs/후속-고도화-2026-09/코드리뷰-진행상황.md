### ✅ 1. 해결됨 — 비밀번호 재설정이 이메일 인증코드를 확인하지 않았다 (2026-09-10 적용)

`FindController.verifyUserForReset`(`POST /reset-password/verify`)이
`userId`+`name`+`email` 일치만 확인하고 **인증코드(OTP)를 전혀 확인하지 않은 채**
비밀번호 재설정 토큰을 발급한다.

프런트(`FindAccountForm.tsx:206`)는 `ev.verifyCode()` 로 클라이언트 화면에서 코드를
확인시키지만, 그건 **버튼 활성화용 UX일 뿐**이고 실제 서버 호출
`POST /reset-password/verify` 에는 `{userId, name, email}` 만 실려 코드가 아예 안 간다.
즉 API 를 직접 두드리면 인증코드 없이 통과한다.

**재현**: 대상자의 아이디·이름·이메일만 알면(이력서·지원서·고객센터 등에서 유출 가능)
`POST /reset-password/verify` 를 직접 호출 → `RESET_TOKEN` 쿠키 획득 →
`POST /reset-password` 로 비밀번호 변경. **메일함 접근 없이 계정 탈취.**

→ 판단 필요: 고치려면 `EmailVerificationService.verifyCode` 가 성공 시 이메일당 검증 상태를
   Redis 에 짧은 TTL 로 남기고(코드 자체는 1회성으로 지워지므로), `verifyUserForReset` 이
   신원 일치 **더불어** 그 검증 상태를 요구하도록 고쳐야 한다. 인증 흐름을 가로지르는
   변경이라 자동화가 밤에 혼자 판단하기엔 위험도가 높아 사람 확인을 기다린다.

**2026-09-10 적용 완료.** RedisRepository 에 markVerified/isVerified/clearVerified 추가,
EmailVerificationService.verifyCode() 가 성공 시 5분 TTL 로 표식을 남기도록 하고,
FindController.verifyUserForReset() 이 신원 일치와 별개로 이 표식을 확인·소모하도록 했다.
프런트는 이미 인증번호 확인을 먼저 시키는 화면 흐름이라 수정 불필요. compileJava 통과.

### ✅ 2. 해결됨 — 알림 읽음처리·삭제에 소유권 검증이 없었다 (2026-09-10 적용)

`NotificationController`(`PATCH`/`DELETE /notifications/{notificationSq}`)와
`NotificationMapper.xml` 의 UPDATE 가 `notification_sq` 만 조건으로 걸고
`receiver_user_sq` 를 안 본다. 로그인만 하면 번호를 증가시켜 가며 **아무나 남의 알림을
읽음 처리하거나 삭제**할 수 있다.

→ 판단 필요: 이것도 diff 밖이라 손대지 않았다. 고치는 자체는 어렵지 않다
   (`WHERE notification_sq = ? AND receiver_user_sq = ?`).

**2026-09-10 적용 완료.** NotificationMapper.xml 의 두 UPDATE 에
`AND receiver_user_sq = #{receiverUserSq}` 추가, 컨트롤러·서비스가 `@AuthenticationPrincipal`
을 전달하도록 시그니처 변경. 프런트·다른 백엔드 호출자 없음 확인. compileJava 통과.

### ✅ 3. 해결됨 — 회원가입이 이메일 인증을 실제로 요구하지 않았다 (2026-09-10 적용)

**2026-09-10 적용 완료.** 개인·기업 가입 폼 둘 다 화면에서 이미 이메일 인증을 필수로
받고 있는 것 확인 후, UserService.signUp() 에 1번과 같은 verified 표식 확인을 추가.
가입 성공 시 표식을 소모한다. compileJava 통과.

### 🔴 5. S3 업로드 컨트롤러가 확장자 검증을 완전히 우회한다 — 실행파일 업로드 가능 (2026-09-10 그룹7 4회차 발견)

`AmazonS3Controller`/`AmazonS3Service`(`POST /api/file` — 업로드, `DELETE` — 삭제)가
이번 마이그레이션이 `FileStorageService` 에 새로 넣은 확장자 화이트리스트
(`SupportedFileTypes`)를 **전혀 거치지 않고** S3 에 그대로 올린다.

- 업로드: 관리자 권한 불필요, 로그인만 하면 `.jsp`/`.php`/`.html`/`.exe` 등 무엇이든 통과.
  바로 이 화이트리스트를 만든 이유(실행 가능 파일이 그대로 저장되는 것)를 옆 컨트롤러가
  그대로 열어 두고 있다.
- 삭제: 클라이언트가 넘긴 `fileName` 으로 지우는데 소유권 확인이 없다(IDOR).

코드베이스 내 다른 호출자(`BoardService`·`AnswerService`·`ResumeService`·
`InformationEditService`)는 전부 이 서비스 호출을 주석 처리하고 `FileStorageService` 로
갈아탄 상태라 **죽은 경로처럼 보이지만, 컨트롤러와 S3 클라이언트 빈(`AwsS3Config`)은
여전히 살아서 요청을 받는다.** `AWS_ACCESS_KEY`/`AWS_SECRET_KEY` 가 설정돼 있다면
실제로 동작한다.

이 파일들은 이번 마이그레이션 diff 에 없다(main 에 이미 있던 코드) — 그래서 diff 기반
자동화 범위 밖이라 손대지 않았다.

→ 판단 필요: 이 컨트롤러를 완전히 지울지(다른 곳에서 안 쓰면), 아니면
   `FileStorageService.validateExtension` 을 재사용하도록 고칠지, 최소한 관리자 전용으로
   잠글지 결정이 필요하다. AWS 자격증명이 실제로 설정돼 있는지부터 확인할 것.

## 실행 규칙 (야간 무인)

1. 아래 표에서 `대기` 인 첫 그룹, 또는 `진행중` 인 그룹을 이어서 한다.
2. `/code-review <경로> --fix` 를 **base 를 명시해서** 돌린다 (아래 「기준 함정」 참고).
3. 같은 그룹을 **최대 5회차**까지 반복한다. 5회차를 채웠거나
   신규 지적이 0건이면 `완료` 로 바꾸고 다음 그룹으로 넘어간다.
4. **명백한 버그만 고친다** — null 가드, 권한 누락, NPE, 언박싱, 오타 수준.
   정책·설계 판단이 걸린 건은 **고치지 말고** 「판단 대기」 절에 적는다.
5. **사람에게 질문하지 않는다.** 야간에는 답할 사람이 없다.
6. 매 회차 끝에 `./gradlew compileJava` (백엔드) 또는 `npm run build` (프런트) 로
   깨지지 않았는지 확인하고, 결과를 이 파일에 적는다.
7. 커밋은 그룹이 `완료` 될 때 한 번만 한다. push 는 하지 않는다.
   (2026-09-10 사용자 결정: **그룹 16 까지 전부 끝난 뒤 한 번에 push 한다.** 그 전까지
   중간에 push 하지 말 것 — origin 은 9커밋 뒤처진 채로 둔다. 지금은 충돌 없이
   push 가능한 상태(`git status -sb` 로 ahead/behind 확인 가능).

## ⚠️ 기준(base) 함정 — 반드시 지킬 것

`/code-review <경로>` 만 주면 diff base 를 **워킹트리**로 잡는다.
이 브랜치는 origin 에 push 되어 있어 `origin/NextJs...HEAD` 가 비어 있으므로
"변경 없음" 으로 판정하고 아무것도 안 본다.

→ args 에 **`git diff main...HEAD -- <경로>` 를 기준으로 보라**고 명시할 것.
   미커밋 변경이 있으면 그것도 함께 보라고 덧붙인다.

## 새 기능이 들어왔을 때

리뷰가 도는 중에 새 기능이 커밋되면, 그 코드가 속한 그룹의 상태를 **`대기` 로 되돌린다**.
`완료` 로 남겨두면 새 코드가 한 번도 검사되지 않은 채 넘어간다.
어느 그룹인지 애매하면 경로로 판단하고, 표에 없는 새 경로면 **행을 추가**한다.

된다. 다 끝나기 전에는 예전처럼 세션 메모리에만 있으므로 `/clear` 하면 죽는다 — 여전히
하지 말 것.

## cron 유지 (재생성 불필요)

(아래는 폐기된 야간 전용 설계의 기록. 참고용으로만 남긴다.)

cron job 은 **세션 메모리에만** 산다. 이 세션을 유지하는 한 매일 밤 자동으로 돈다.
`/clear` 를 하면 사라지므로 **하지 말 것** — 09시에 필요한 건 세션 초기화가 아니라
**새 사용량 블록이 열리는 것**이고, 그건 04:07 이후 조용히 두면 저절로 된다.

혹시 세션이 끊겨서 다시 걸어야 하면 Claude 에게 이렇게 말하면 된다:

> 야간 코드리뷰 cron 다시 걸어줘

- cron: `7 18-23,0-4 * * *`
- recurring: true
- 프롬프트: 이 파일의 「실행 규칙」·「기준 함정」·「재지적 금지 목록」 을 따르는 무인 리뷰 지시
  (AskUserQuestion 금지, 명백한 버그만 수정, 판단 필요 건은 「판단 대기」 에 기록,
   429 면 조용히 끝내고 다음 발화에서 재개, 05시 이후 새 작업 금지, 한 줄 보고)

**전제**: 터미널을 켜둔 채 퇴근해야 한다. cron 은 REPL 이 유휴일 때만 발화한다.
recurring cron 은 7일 후 자동 만료된다.

## 커버리지 확인

그룹을 고쳤으면 이 명령으로 빠진 파일이 없는지 확인한다.

```bash
git diff main...HEAD --name-only \
  | grep -v -E '^(backend/src/(main/(java|resources)|test)|frontend/nextjs/(lib|stores|hooks|types|components|app|public|Dockerfile|\.dockerignore|next\.config|proxy|package|tsconfig|eslint|postcss)|frontend/react_js/(src|\.dockerignore|\.env)|deploy|backend/(Dockerfile|\.dockerignore)|docs/|\.gitignore)' \
  | grep -v -E '\.(png|jpg|jpeg|webp|svg|ico|css|md)$'
```

**소스 파일이 하나도 안 뜨면 정상**이다. 소스가 뜨면 그룹 표에 넣어라.

### 3. 모집인원 정렬이 공통코드 값 순이다 — ✅ 해결됨(2026-09-14)

스키마 변경 없인 SQL join 이 불가능함을 확인 — 대신 기존 서열 산출 로직
(`DeveloperGradeSupport.sortKeyOf`, 영문명 기반)을 재사용하는

순서 유지.

### 6. 공고 목록 API 의 size 파라미터가 검증되지 않는다 — ✅ 해결됨(2026-09-14)

`ProjectController.getProjectList`/`getProjectRegionGroups` 에 `@Valid` 추가.
`BaseRequest` 의 기존 `@NotNull`/`@Min(1)` 이 이제 실제로 걸린다. 프런트 소비처
(`ProjectListClient`, `app/projects/page.tsx`, `app/sitemap.ts`) 전부 page/size 를
항상 보내는 것을 확인해 기존 정상 흐름은 안 깨진다.

### 9. 공고 목록 한 화면에 쿼리가 140여 회 나간다 (성능, 결정 사안 아님— 참고용)

목록 한 행마다 상태판정+주소조회(2)+스크랩+기업이미지+기술+모집인원 조회가 돈다.
`WHERE project_sq IN (...)` 배치 조회로 접어야 하지만 응답 조립 구조를 바꿔야 해서
범위가 크다. 필요시 별도 작업으로.

### 10. 공고 주소 수정 시 옛 우편번호가 새 주소에 복사된다 — ✅ 해결됨(2026-09-14)

### 15. 소프트삭제된 이력서가 여전히 읽히고 복사된다 — ✅ 해결됨(2026-09-14)

`findUserByResumeSq`/`selectResumeByResumeSq` 를 부르는 모든 곳(`requireResumeOwner`,
`requireResumeReadable`, `requireResumeChangeableByAffiliate`, 지원시 이력서 소유권
검증)이 "먼저 소유권/열람권을 확인 → 통과하면 상세 조회" 순서로만 쓰임을 확인 —
이미 같은 이력서를 다루는 `ResumeDetailMapper.selectResumeBasic` 등 다른 조회는
`resume_is_deleted_yn = 'N'` 을 이미 걸고 있어 동작 불일치이기도 했다. 두 쿼리에
같은 조건을 추가해 소프트삭제된 이력서는 소유자 확인부터 실패("이력서를 찾을 수
없습니다")하도록 통일했다.

### 30. lib/fetchers.ts safeGet() 이 네트워크/5xx 에러를 404 취급한다 — ✅ 해결됨(2026-09-14)

백엔드는 삭제/미존재 게시글·공고도 400 으로 응답한다(컨트롤러가 던지는
`IllegalArgumentException` 이 `GlobalExceptionHandler` 에서 400 매핑). `safeGetDetailed()`
를 추가해 4xx 만 `confirmedMissing: true` 로 보고, 5xx·네트워크 예외는 `false` 로 구분한다.
`getBoardDetail`/`getQnaDetail`/`getNoticeDetail`/`getProjectDetail` 이 이 detailed 버전을
반환하도록 바꾸고, 5개 상세 페이지의 `generateMetadata` 가 `confirmedMissing` 일 때만
`robots.index = false` 를 준다(React `cache()` dedupe 유지를 위해 별도 함수를 새로 만들지
않고 기존 4개 export 를 이 버전으로 교체했다 — 안 그러면 같은 자원을 두 번 fetch하게 됨).
