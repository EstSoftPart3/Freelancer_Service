# 1. 인터뷰 가능시간 — 「협의 후 인터뷰 진행」

## 요청 내용 (팀 피드백)

> 인터뷰 가능시간에 **'협의 후 인터뷰 진행'** 같은 것도 만들었으면 좋겠다.
> 일일이 (시간을) 찍기 귀찮은 사람들이나, 진짜 협의 후 진행해야 하는 사람들을 위해 필요할 것 같다.

## 왜 지금 안 하는가

**좋은 의견이지만, 이 옵션만 넣으면 흐름이 끊긴다.**
「협의 후 진행」을 고른 공고는 **슬롯이 하나도 없는 상태로 지원을 받게 되는데**,
지금 구조에서는 지원자가 슬롯 중 하나를 고르는 것 말고는 인터뷰를 잡을 방법이 없다.
즉 **"추후 인터뷰를 잡을 때 시간을 협의하는 기능"이 함께 있어야 완결된다.**
그 협의 기능이 이 항목보다 큰 작업이라 **후속 서비스 기능으로 분리**한다.

## 현재 구조 (착수 전에 읽을 것)

인터뷰 시간은 **공고 등록 시점에 기업이 슬롯을 전부 찍어 두고, 지원자가 그중 하나를 고르는**
한 방향 구조다. 협의라는 개념 자체가 없다.

| 단계 | 위치 |
|---|---|
| 기업이 슬롯 등록 | `frontend/nextjs/components/project/InterviewTimeModal.tsx` (날짜 목록 + 30분 단위 시간 그리드) |
| 등록 폼 필수 검증 | `components/mypage/company/ProjectPostClient.tsx:323` — `interviewTimes.length === 0` 이면 **등록 차단** |
| 저장 | `TBL_PROJECT_INTERVIEW_TIME_SLOT_S` (`interview_available_dtm`), `mapper/project/ProjectMapper.xml:526` |
| 지원자가 슬롯 선택 | `components/mypage/common/InterviewSelectModal.tsx` → `PATCH /projects/applications/interviews/{slotSq}` |
| 확정 결과 | `TBL_PROJECT_APPLICATION` 의 `selected_interview_dtm` (`ProjectApplicationEntity:35`) |
| 일정 노출 | `mapper/mypage/ScheduleMapper.xml` (마이페이지 캘린더) |

**핵심 제약: 슬롯이 0건인 공고를 지금 구조는 상정하지 않는다.**
`ProjectPostClient.tsx:323` 의 필수 검증을 푸는 순간, 지원자 화면(`InterviewSelectModal`)은
빈 목록이 되고 `selected_interview_dtm` 은 영원히 `null` 로 남는다.

## 착수 시 손봐야 할 곳 (스케치)

1. **공고 쪽 플래그** — "협의 후 진행" 여부를 담을 자리가 필요하다.
   슬롯 테이블에 특수 행을 넣는 방식은 피할 것(`interview_available_dtm` 이 NOT NULL 성격).
   공고 본체에 컬럼(예: `interview_negotiable_yn`)을 두는 편이 안전하다.
2. **등록 폼** — 「협의 후 진행」 체크 시 `ProjectPostClient.tsx:323` 필수 검증을 면제하고,
   `InterviewTimeModal` 진입 버튼을 비활성화한다.
3. **공고 상세** — 인터뷰 가능시간 자리에 "협의 후 진행" 문구를 보여준다.
4. **지원 흐름** — `InterviewSelectModal` 이 슬롯 선택 대신 "협의 요청" 상태로 넘어가야 한다.
   여기서 **선행 작업(아래)** 이 없으면 막힌다.
5. **일정 캘린더** — 시간이 정해지지 않은 인터뷰를 어떻게 표시할지 정해야 한다(`ScheduleMapper.xml`).

## 🔴 선행 작업 — 인터뷰 시간 협의 기능

**이것이 없으면 위 4번에서 멈춘다.** 최소한 다음이 필요하다.

- 지원 이후 기업 ↔ 지원자가 시간을 **주고받는** 수단 (기업이 후보 시각 제시 → 지원자 수락/역제안)
- 그 과정의 **상태 값** (협의중 / 확정 / 무산) — 지금은 `selected_interview_dtm` 유무가 곧 확정 여부다
- 확정 시점에 `selected_interview_dtm` 을 채워 **기존 캘린더·지원현황과 합류**시키는 지점

## 함께 검토할 것

- 「일일이 찍기 귀찮다」는 쪽 요구는 **협의 기능 없이도** 완화할 수 있다 —
  예: 요일·시간대 일괄 선택(월~금 14:00~18:00 전체 체크) 같은 입력 보조.
  협의 기능보다 훨씬 작고, `InterviewTimeModal` 안에서 끝난다.
  협의 기능 착수가 미뤄진다면 **이쪽을 먼저 검토할 가치가 있다.**

# 2. 게시글 삭제 시 답변 캐스케이드 (2026-09-08 추가)

## 문제

`BoardService.deleteBoard` · `AdminBoardService.deleteBoardMaster` 는 게시글만 소프트삭제하고
자식 답변 행(`answer_is_deleted_yn`)은 `'N'` 그대로 남긴다.

2026-09-08 code-review 에서 BO 게시물 관리 목록에
**부모가 이미 삭제된 답변이 `mainType=ANSWER` 로 계속 노출**되는 것이 확인돼,
`AdminBoardMapper.xml` 목록·카운트 쿼리에 `AND pb.board_is_deleted_yn = 'N'` 을 넣어 가렸다.

**즉 지금은 증상만 가린 상태다.** 그 결과 부작용이 하나 생겼다 —
과거 삭제로 이미 고아가 된 답변 행들은 이제 BO 화면에서 보이지 않고,
소프트삭제를 걸 수 있는 유일한 화면(`deleteAnswerMaster`)에서 사라졌으므로
**영구히 접근 불가한 행**이 되었다.

## 착수 시 손봐야 할 곳

1. **삭제 경로 캐스케이드** — `BoardService.deleteBoard`, `AdminBoardService.deleteBoardMaster`
   양쪽에서 자식 답변도 함께 소프트삭제. FO·BO 두 경로가 다르므로 둘 다 봐야 한다.
2. **기존 고아 데이터 정리** — 부모가 이미 `Y` 인데 자식이 `N` 인 답변 행을 일괄 정리.
   운영 DB 작업이므로 `docs/도구/*` 규칙(백업 → 개발DB 검증 → 드라이런 → `--prod --apply`)을 따를 것.
3. **가림막 제거 검토** — 1·2 가 끝나면 `AdminBoardMapper.xml` 의
   `pb.board_is_deleted_yn = 'N'` 조건이 계속 필요한지 다시 판단한다.

## 함께 남겨둔 결정 (2026-09-08, 그대로 두기로 함)

- **시드 작성자 정책 비대칭** — 시드 등록은 `botOnly=false`(실계정 작성자 허용), 회수는 `botOnly=true`(봇만).
  실계정 명의로 등록한 시드는 회수 도구로 지울 수 없다. 의도된 동작으로 보고 두기로 했으며,
  필요 시 DB 에서 직접 정리한다. (`AdminSeedService.resolveAuthors`)
- **`SeedPlanner.naturalTimeOn` 08시 이전 폴백** — `now.minusMinutes(1~60)` 이라
  자정 직후 `TODAY` 시드가 전날 날짜로 넘어갈 수 있다. 실무상 무해하다고 판단해 두었다.
- **빈 답변 가드 미적용 경로** — `AdminBoardController` 의 Q&A 답변 등록(`POST /admin/board/answer`)은
  VOC 와 달리 여전히 빈 본문을 막지 않는다(`AnswerService.createAnswer` 는 `null` 만 거른다).
  FO 경로까지 영향이 가므로 별도 판단이 필요하다.
