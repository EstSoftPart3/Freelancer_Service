# 항목 1. 서버 에러 메시지 유실 전수 점검

## 무엇이 문제인가

백엔드 일부 컨트롤러가 `ApiResponse` 를 **`ResponseEntity` 로 감싸지 않고 그대로 반환**한다.
그러면 실패해도 **HTTP 는 200** 이고, 실패 여부는 본문의 `status` 필드에만 있다.

```json
HTTP 200
{ "status": "UNAUTHORIZED", "message": "비밀번호가 일치하지 않습니다.", "output": null }
```

프런트 `frontend/nextjs/lib/api.ts:42-53` 의 **성공 인터셉터**가 이걸 `reject` 로 바꾼다.

```ts
if (d && typeof d === 'object' && 'status' in d && d.status !== 'OK' && d.status !== 'CREATED') {
  const err = Object.assign(new Error(d.message ?? '요청 처리에 실패했습니다.'), { response: res })
  return Promise.reject(err)
}
```

**그 결과 두 가지가 동시에 벌어진다.**

1. Vue 에서 옮겨온 `if (data.output) {...} else { data.message }` 구조에서 **`else` 가 죽은 코드**가 된다.
2. 인자 없는 `catch { }` 가 실행되어 **서버가 보낸 구체적인 메시지가 통째로 버려진다.**

`PasswordCheck.tsx` 가 정확히 이 모양이었고, 이번에 그 한 곳만 고쳤다.

## ⚠️ 전수 치환하면 안 된다

인자 없는 `catch` 는 프런트에 **60곳 이상** 있지만 **대부분은 고칠 필요가 없다.**
"게시글을 불러올 수 없습니다" 같은 조회 실패에 서버 문구를 그대로 노출하면 오히려 나쁘다.

**고쳐야 하는 것은 서버가 "사용자가 알아야 할 이유"를 담아 보내는 경우다** —
비밀번호 불일치, 중복 아이디, 형식 오류, 탈퇴 거절 사유 등.

### 특이 케이스 두 개

**`GET /mypage/projectScrap` — 스크랩이 0건일 때 `NOT_FOUND` 를 준다.**
정상 상태를 에러로 내려주는 셈이라, 프런트가 이미 개별 우회를 해 뒀다.
`mypage/personal/ProjectScrapClient.tsx:47-58` 의 주석이 이 문제 전체를 잘 설명하고 있으니
**작업 전에 이 주석부터 읽을 것.** 근본 해결은 백엔드가 빈 목록을 200 OK 로 주는 것이다.

(`SignUpController.java:23-26`). 같은 파일의 `check-nickname` 은 `ApiResponse` + "사용 가능" 기준이라
**둘의 의미가 서로 반대다**(주석에도 명시돼 있다). 정리 대상.

## 어떻게 고칠까 — 두 갈래

**(A) 프런트만 고친다 (안전, 권장)**
이미 만들어 둔 `frontend/nextjs/lib/errors.ts` 의 `getApiErrorMessage(err, fallback)` 를 쓴다.
`catch {}` → `catch (err)` 로 바꾸고 fallback 은 지금 문구를 그대로 둔다.
위 표의 ★ 이상만 손대면 된다. 회귀 위험이 거의 없다.

```ts
} catch (err) {
  toast.error(getApiErrorMessage(err, '회원 탈퇴 처리에 실패했습니다.'))
}
```

**(B) 백엔드를 `ResponseEntity` 로 통일한다 (근본적, 위험)**
🔴 **그냥 하면 안 된다.** 실패를 `401` 로 바꾸면 `lib/api.ts:59` 의 **refresh 인터셉터가 가로채**
"세션이 만료되었습니다" 를 띄우고 **로그인 페이지로 튕긴다.**
→ 인증 실패가 아닌 검증 실패는 반드시 `400` 을 쓰고, 프런트 인터셉터도 함께 검토할 것.

**권장: (A) 로 화면을 먼저 정상화하고, (B) 는 별도 과제로 분리한다.**
