## Context

Vue→Next.js 마이그레이션이 끝나고 QA까지 마친 시점에서, 운영을 시작하기 위한 고도화 요구사항 20여 건이 한꺼번에 들어왔다. 성격이 제각각이다 — 모바일 UI 깨짐 같은 즉시 수정 건, 닉네임 도입처럼 DB부터 FO·BO까지 관통하는 건, 고객의 소리·BO 관리 페이지 같은 신규 기능, 그리고 실서버를 아직 구 Vue가 서빙 중이라 남아 있는 배포 과제.

의존성이 얽혀 있어 순서가 중요하다. **DB 이관이 모든 것을 막고**, 닉네임 컬럼이 관리자·봇 계정 생성을 막고, 카테고리와 고객의소리가 봇 자동화를 막는다. 배포는 사용자 결정에 따라 전 기능 완료 후 마지막에 일괄 진행한다.

### 확정된 결정사항
| 항목 | 결정 |
|---|---|
| 배포 시점 | 전 기능 완료 후 일괄 배포 (Phase 9) |
| 닉네임 이관 | `user_id` 기반 자동 생성(중복 시 접미사) + 마이페이지에서 변경 |
| 스키마 정리 | **최소 범위** — 신규 기능에 필요한 것 + 불필요 테이블 정리만 |
| DB 이관 | `freelancer_education` → 기존 `project` DB. **개발 착수 전 최우선**. 원본은 다른 곳에서 사용 중이라 **보존** |
| 봇 자동화 | 백엔드 비내장. 독립 스크립트 + cron, 봇 계정으로 공개 API 호출 |

### 착수 전 발견한 선결 이슈 (검증 완료)

`@Entity`가 붙은 클래스 17개 중 **`@Table`이 있는 것은 `Project.java`, `ProjectApplicationEntity.java` 2개뿐**이다. 나머지 15개는 무매핑 상태이고, `application.yml:36`이 `ddl-auto: update` + `PhysicalNamingStrategyStandardImpl`이므로 Hibernate가 클래스명 그대로(`Board`, `Answer`, `Address`…) 테이블을 자동 생성한다. 실데이터는 MyBatis가 쓰는 `TBL_*`에 있으므로, 이 15개는 빈 껍데기 고아 테이블이다.

```
domain/affiliation/entity/  Address, AreaCd, Career, CompanyApplication, ResumeSkillTag, Scrap
domain/community/entity/    Answer, Board, BoardAttachment, Comment, CommonSkillTag,
                            NormalTag, Recommendation, SkillTag
domain/community/dto/response/BoardAttachmentResponse   ← DTO에 @Entity가 잘못 붙음
```

새 DB에 앱을 붙이는 순간 그쪽에도 고아 테이블이 재생성되어 이관 검증이 오염된다. **Phase 0의 첫 작업**으로 처리한다. (`BoardRepository`는 선언만 있고 호출처 0건 — dead code)

문서 최상단([진행 상태 보드](#진행-상태-보드))에 있다. **Phase 완료 시마다 갱신**한다.

1. `docs/고도화-실행계획.md`를 읽고 상태 보드에서 **다음 Phase**를 확인
2. 직전 Phase의 **완료 기록**(아래 형식)을 읽어 무엇이 끝났고 무엇이 남았는지 파악

4. **이번 Phase 계획을 사용자와 함께 재검토** — 지난 Phase에서 드러난 사실 때문에 수정할 부분이 있는지 확인하고, 합의 후 착수

**핵심 판정**

4. **`freelancer_project` 전용 `tbl_faq_m`(26행), `tb_faq_m`도 우리 코드 미사용** → 건드리지 않고 그대로 둔다.
5. **기술태그만 `freelancer_project`가 우세.** 52개이고 현행 24개는 그 부분집합. → 이관 후 별도 추가(사용자 결정).

**확정된 방향**: `freelancer_project`의 앱 테이블 43개를 백업 후, `freelancer_education`의 현행 데이터로 **완전 교체**.

### 0-B. 코드 선정리 — JPA 완전 제거 (이관 전 필수)

실사 중 확인: **이 프로젝트는 JPA를 전혀 쓰지 않는다.**
- `JpaRepository` 상속은 `BoardRepository` 하나뿐이고 **호출처 0건**(dead code)
- `EntityManager` 직접 사용 **0건**
- 그 외 `*Repository`는 전부 `@Repository` 스테레오타입을 단 **MyBatis 매퍼 래퍼**
- `@Entity` 클래스 17개는 실제로는 **MyBatis resultType용 POJO**로 쓰인다 (`AffiliationService`, `BoardService`, `AdminBoardService` 등에서 import)

그런데 `@Entity` + `ddl-auto: update` 때문에 Hibernate가 클래스명 그대로 테이블을 자동 생성하고 있다. `freelancer_education`·`freelancer_project` 양쪽에 이미 15개가 만들어져 있다(`address`, `answer`, `board`, `comment`, `scrap`, `skilltag`, `boardattachmentresponse` 등, 전부 0행).

**조치 — 클래스는 살리고 JPA 어노테이션만 걷어낸다.**

| 대상 | 조치 |
|---|---|
| `@Entity` 17개 클래스 | `@Entity`/`@Table`/`@Id`/`@GeneratedValue`/`@Column` 등 `jakarta.persistence.*` **제거**. 클래스 자체는 MyBatis POJO로 계속 사용하므로 **삭제하지 않는다** |
| `domain/community/repository/BoardRepository.java` | **삭제** (유일한 JPA 리포지토리, dead code) |
| `domain/community/dto/response/BoardAttachmentResponse.java` | DTO에 `@Entity`가 붙어 있음 → 제거 |
| `application.yml` | `ddl-auto: update` → **`none`**, `generate-ddl: true` → `false` |

효과: 새 DB에 붙여도 고아 테이블이 생기지 않는다. 기존 15개는 이관 시 양쪽에서 DROP.

> 계획 초안은 "`@Table`을 명시하거나 삭제"였으나, 실사 결과 **JPA 자체가 미사용**이라 어노테이션 제거가 정답이다.

### 0-C. 이관 실행

대상은 **앱 실사용 43개 테이블**(매퍼 XML에서 추출). 스크립트 `docs/db-migrate.py`로 수행한다.

```
1. 백업    freelancer_project의 43개 테이블 → 덤프 파일 + `_bak_20260728` 스키마
2. 정리    freelancer_project의 43개 테이블 DROP, 고아 테이블 15개 DROP
           (tbl_faq_m, tb_faq_m 은 보존 — 우리 코드 미사용이지만 남의 데이터)
3. 이관    freelancer_education의 43개 테이블 스키마+데이터 복사
           FOREIGN_KEY_CHECKS=0, AUTO_INCREMENT 값까지 승계
4. 검증    양쪽 COUNT(*) / MAX(pk) / CHECKSUM TABLE 대조
```

**FK 4건**(`board_comment_s.parent`, `notification_m.receiver`, `schedule_m.type_cd`, `user_online_s.user`)이 있으므로 DROP/INSERT 시 `SET FOREIGN_KEY_CHECKS=0` 필수.

**이관 후 별도 작업** — 기술태그 28개(TypeScript, Next.js, AWS, Kubernetes, PostgreSQL, Jira 등) `TBL_SKILL_TAG_C`에 새 sq로 INSERT.

2. **상세 API에 좌표가 없었다** — `ProjectDetailResponse`에 `latitude`/`longitude`를 추가해야 서버 리다이렉트가 성립했다. `findBySq` 쿼리는 이미 좌표를 반환하고 있어 DTO 2필드 추가로 끝났다.

4. ~~**출발지(사용자 위치) 자동설정 제거**~~ → **2026-07-29 사용자 결정으로 원복.** 카카오 링크 규격상 좌표 노출을 어차피 피할 수 없어(서버 리다이렉트를 경유해도 브라우저가 결국 그 URL로 이동한다) 출발지 자동설정이라는 실질 UX만 잃는 거래였다. `app/directions`·`lib/kakaoMap.ts`·`ProjectDetailResponse` 좌표 필드 전부 제거하고 예전 방식 복원.
   원복하면서 남은 위험만 추가로 막았다 — `noopener,noreferrer`(역탭내빙·Referer 누출 차단), 좌표 `Number.isFinite` 검증(경로 구분자 주입 방지).
   **참고: `userStore`의 `latitude/longitude`는 실시간 GPS가 아니라 `/me`가 내려주는 가입 시 등록 주소 좌표다.** 즉 URL에 실리는 건 사용자의 등록 주소이며, 브라우저 히스토리와 카카오 서버 로그에 남는다. 공용 PC 사용 시 이전 사용자의 주소가 히스토리로 노출될 수 있다는 점은 알고 있어야 한다.
5. **XSS 대응은 DOMPurify 대신 `escapeHtml`** — 삽입 대상이 전부 순수 텍스트(제목·회사명·주소)라 이스케이프가 정확하다. DOMPurify의 태그 스트립은 `a < b` 같은 텍스트를 손상시킨다.
6. **`ResponseStatusException` 핸들러 추가(계획 외)** — 없으면 `handleGeneralException(Exception)`이 먼저 잡아 확장자 거부 400이 전부 500으로 나간다. A-2의 "한글 에러" 요구가 이것 없이는 성립하지 않았다.
7. ~~**`.svg` 화이트리스트 제외**~~ → **2026-07-29 사용자 결정으로 허용.** 대신 실제 위험 경로를 막았다.
   `FileController`는 `download=false`일 때 `Content-Disposition: inline`으로 응답한다 — `.svg`를 주소창으로 직접 열면 브라우저가 문서로 렌더링해 내부 `<script>`가 **우리 오리진에서 실행**된다. `accessToken` 쿠키가 httpOnly가 아니라(`lib/api.ts`가 `document.cookie`로 읽는다) 토큰 탈취까지 이어질 수 있는 경로였다.
   → 응답에 `Content-Security-Policy: sandbox`(고유 opaque 오리진으로 격리) + `X-Content-Type-Options: nosniff` 추가. **이 헤더는 svg 허용과 한 쌍이다 — 지우면 곧바로 저장형 XSS가 된다.**
   `<img>`로 삽입한 이미지 표시는 영향 없다(sandbox는 문서로 로드될 때만 적용). 기존 파일 8건 Content-Type 확인 결과 octet-stream 0건이라 nosniff 회귀도 없다.

→ **`<when test="searchType == '회사명'">` 신설**(`TBL_COMPANY_S c ... c.company_nm LIKE`)하고, `'작성자명'` 죽은 분기는 제거한다. Phase 3-A가 같은 매퍼(`selectMainPopularProjects`)를 손대므로 함께 처리한다.

1. **카테고리 라벨을 FO에 하드코딩하지 않았다.** 계획대로 `GET /community/board-categories`를
   만들고 FO는 `useBoardCategories`로 받아 쓴다. 하드코딩 배열은 첫 페인트/조회 실패용 **폴백**으로만
   남겼다. 덕분에 **라벨 변경은 공통코드 UPDATE 하나로 끝나고 재배포가 필요 없다.**
2. **양식 주입에 `clipboard.dangerouslyPasteHTML`을 쓰지 않았다.** `ReactQuill`이 이미
   `value={description}` 제어 컴포넌트라 state를 넣으면 그대로 반영된다. `next/dynamic`으로 로드한
   컴포넌트는 ref가 전달되지 않아 에디터 인스턴스를 잡으려면 래퍼가 하나 더 필요한데, 그럴 이유가 없었다.
3. **BO 작성 폼에도 카테고리 select를 넣었다(계획 외).** 계획의 BO 범위는 "컬럼 + 필터"였는데,
   그러면 **BO에서 만든 일반 게시글은 영구히 미분류**가 된다. 관리자가 카테고리를 볼 수는 있는데
   지정할 수는 없는 상태라 버그로 신고될 것이다. 상세 DTO에 `boardCategoryCd`를 추가해 수정 시
   초기값도 채운다.
4. **`board_type_cd` 체계는 손대지 않았다.** Phase 3 인계 1번 항목대로 `findBestBoards`의
   `IN (1401,1402)`도 그대로다 → **베스트글 집계 범위와 3-B 안내 문구가 여전히 일치한다.**

**함정 3건 (기억할 것)**

1. **`JwtAuthenticationFilter.EXCLUDE_URLS`가 `SecurityConfig`와 별개인 두 번째 화이트리스트다.**
   `SecurityConfigProd`에 `/community/**` permitAll이 있는데도 새 엔드포인트가 **401**을 뱉었다.
   이 필터는 **접두사 매칭**이라 `/api/community/boards`가 `/api/community/board-categories`를
   덮지 않는다. 더 나쁜 건 **매핑이 없는 경로도 이 필터가 401로 만든다**는 점 —
   `/api/nonexistent-root`도 401이라 "404인가 401인가"로 원인을 가릴 수 없었다.
   → **공개 GET을 새로 만들면 SecurityConfig와 이 목록 양쪽에 넣을 것.**
2. **`BoardMapper.update`가 카테고리를 무조건 덮어쓴다.** `updateStatusBoard`(Q&A 채택 상태 변경)도
   같은 `update`를 호출하는데, 그쪽은 `findByIdBoard`(`SELECT *`)로 읽은 엔티티를 그대로 넘기므로
   카테고리가 보존된다. 서비스에서도 **요청에 `categoryCd`가 실려 왔을 때만** 덮어쓰도록 막았다
   (공지 수정처럼 카테고리를 안 보내는 호출부가 값을 지우지 않게).
3. **미분류(null)를 '자유'로 승격하지 않았다.** `BoardCategoryCode.labelOf(null)`은 '자유'를
   돌려주지만 DTO에서는 **null이면 라벨도 null**로 내린다. 승격하면 "기존 글 전부가 자유 카테고리"로
   보이는데 실제로 자유를 고른 글과 구분이 사라지고, 카테고리 탭 '자유'를 눌렀을 때
   (SQL은 `= 3201`) 목록과 뱃지가 어긋난다.

**동시 정리**: `sidebar-data.ts:105`의 `/events/ranking`은 라우트 없는 깨진 링크 — 제거.

#### 🟢 Phase 5에서 넘어온 것 — Phase 6에 바로 쓸 재료 (2026-07-30 추가)

**BO 신규 화면은 `features/voc/` 를 베껴 쓰는 게 가장 빠르다.** Phase 5에서 만든 최소 구성이
`features/board/`(12파일, 드로어·다이얼로그·벌크액션 포함)보다 훨씬 작고, 6-A/6-B가 필요한 것과 모양이 같다:

```
features/voc/
  index.tsx                     ← getRouteApi + URL 파라미터 ↔ 목록 조회, 검색어 디바운스
  api/voc-api.ts                ← URLSearchParams 조립 (false 도 유효값인 필터 처리 주의)
  data/schema.ts                ← 목록 zod + 상세 interface
  components/voc-provider.tsx   ← open/currentRow + refresh 콜백
  components/voc-table.tsx      ← 서버 페이징·정렬·패싯필터
  components/voc-columns.tsx    ← 셀 컴포넌트 분리(훅 사용 때문)
  components/voc-view-drawer.tsx / voc-dialogs.tsx
routes/_authenticated/contents/voc/index.tsx   ← validateSearch zod
```

Phase 5에서 실제로 밟은 함정:
- **`answered` 같은 boolean 필터는 `if (params.x)` 로 거르면 안 된다** — `false`가 유효값이라 조용히 빠진다.
  `!== undefined` 로 볼 것. 6-B의 모집상태·삭제여부 필터에 그대로 해당한다.
- **패싯 필터가 서버 boolean 하나에 대응할 때**, 옵션 두 개를 다 고르면 "전체"와 같다 —
  `picked.length !== 1` 이면 필터를 보내지 않는 처리가 필요하다(`voc-table.tsx` 참조).
- **`routeTree.gen.ts` 는 빌드/dev 시 자동 갱신**된다. 라우트 파일만 만들고 `npm run build` 하면 된다.
- **`DataTableToolbar` 는 `columnId` 로 컬럼을 찾는다** — 컬럼 `id` 와 필터 `columnId` 가 어긋나면
  필터 UI 가 조용히 렌더되지 않는다.

**관리자 삭제는 반드시 마스터 쿼리를 쓸 것.** `BoardService.deleteBoard` 처럼 `AND user_sq = #{userSq}`
가 붙은 쿼리를 관리자 경로에서 부르면 **남의 데이터에 0행이 반영되고 조용히 성공**한다.
6-B의 프로젝트 soft delete 도 같은 함정이 있다(`ProjectMapper` 의 삭제 쿼리 조건을 먼저 확인할 것).

**정렬 필드는 BO 컬럼 `id` 가 그대로 `sortField` 로 온다.** 매퍼 `<choose>` 의 `<when>` 문자열과
컬럼 id 가 어긋나면 `otherwise` 로 조용히 폴백된다(무증상). `SortDirectionUtil.normalize` 는 필수.

**목록·카운트 쿼리는 `<sql>` 조각을 공유시킬 것.** 한쪽만 조건을 늘리면 "목록은 맞는데 총 건수만
전체 기준이라 뒷 페이지가 비는" 증상이 난다(Phase 3 사례, Phase 5에서도 같은 구조로 만들었다).
